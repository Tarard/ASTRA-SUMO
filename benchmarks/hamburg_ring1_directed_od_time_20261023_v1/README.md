# 汉堡单 OD 时段定向调整：原生计数反馈试验

本包保留两项有界候选及全部失败记录。两项均被拒绝，MAE 尚未归零。
输入基线是 [LSA119 回折修复后的完整原生评价](../hamburg_ring1_119_straight_order_20261023_v1/README.md)。
基线没有碰撞或传送，但有 1381 辆未进入、409 辆在途，字段诊断 MAE 为 16.730769。

## 一项明确的调整

路网、控制程序、检测器、真实观测、车道行为及全网请求总数保持不变。
只在 `142944473#0 → 28665128#0` 这一组 OD 内重新分配出发时段数量。
每个时段最多调整 4 辆，迁移总量最多 12 辆。全网仍请求 8603 辆，每组 OD 的总量保持不变。
这些限额是首项小试验的工程边界，不是文献证明的最优参数。

已有 264 个非空 OD 时段的逐车记录提供本次实际通过比例。
其余 30 个没有请求的时段保持原值，不编造响应。
全部 130 项真实字段观测都进入目标，不删除难匹配字段或时段。
在候选筛选中，分别检查各 OD 的有界整数时段分配，以 130 项总绝对误差和改动量选择一项方案。
所有时段按一次完整原生运行取得的比例估计，**这些比例不是改变需求后的因果导数**。

候选在这个近似下预测总绝对误差从 2175 降至 2151，不能当作新的 SUMO 计数。
`proposal.json` 保存实际提交仿真的向量，`response.npz` 和 `columns.json` 保存比例、分子、分母和时段顺序。
`native-identity-reconciliation.json.gz` 保存逐车过检提取记录、所有周期 E1 的对应比较及原始即时文件哈希。
提取的完成通过事件与周期 E1 `nVehContrib` 对齐，没有以进入事件替代。

继承的经验分位数生成方式会连带重排同一时段内的请求时间和模板。
因此，12 辆的时段数量迁移实际改变了 219 个请求的 XML。
这不是“只改动 12 个具体车辆”的试验。八个被调整时段之外的请求保持一致，见 `preflight.json`。
路线和车道模板仍是已有经验先验，不是现场真实 OD 或自然驾驶的证明。

## 原生核验规则

每次均从空网开始，步长 0.1 秒、种子 104，运行至 14400 秒。
仅使用原生 E1 `nVehContrib`，取得全部 130 项字段和 40 项派生站点值。
站点值是字段求和，不增加独立证据。
只有无碰撞、无传送、无丢弃、MAE 下降、最大误差不增加，且未进入与在途总数不增加，才保留为诊断改善。
即使满足这项小步规则，仍须达到运行有效及全部 130 项零残差，才能通过最终计数验收。

首个执行进程在约 11106.2 秒处停止，没有完整评价或最终计数表，原因未定。
其原生文件以 `.partial.xml.gz` 保留在 `interrupted-attempt/`。
这些文件不完整，不计算全窗口 MAE，也不把缺失时段填零。
同一候选随后从空网重跑，结果单列。没有使用未验证的保存状态续跑。

## 根据实测差值收缩动作

## 运行耗时

`timing.json` 记录每次 144000 步的原生运行耗时。
第一项完整候选耗时 977.456 秒，其中 TraCI 交互阶段为 553.109 秒，约占 56.6%。
这个时间包含命令处理和外部客户端交互，不能全部归为纯网络传输。
0.1 秒步长及逐步交互都影响速度；直接改粗步长可能改变计数及碰撞结果。

## 离线复核与重建输入

在仓库自己的 uv 环境中执行：

```powershell
$env:PYTHONUTF8='1'
$env:PYTHONPATH="$PWD/plugins/astra-sumo/src"
$env:SUMO_HOME="$PWD/.venv/Lib/site-packages/sumo"
$env:PATH="$env:SUMO_HOME/bin;$PWD/.venv/Scripts;$env:PATH"
.venv/Scripts/python.exe -m pytest -q tests/test_od_time_redistribution.py
.venv/Scripts/python.exe benchmarks/hamburg_ring1_directed_od_time_20261023_v1/prepare.py --output-dir outputs/hamburg-directed-new
```

`prepare.py` 从冻结需求、出入记录和过检身份重建全部比例及候选，并核对请求总数。
这一步不启动 SUMO。大体积即时 E1 的原路径和哈希仍在对应清单中，完整源事件的再次提取需要迁移这些文件。
现有计数、逐车归属及候选算术的复核可使用 Git 中的冻结记录。
正式接受前仍须核对并声明控制方案，不能把冻结程序等同于现场真实 SPaT。
需要复测第一项时，使用 `measure.py --prepared-dir outputs/hamburg-directed-new/prepared --proposal outputs/hamburg-directed-new/proposal.json --output-dir outputs/hamburg-directed-new/evaluation`。
第二项使用同一准备目录，将 proposal 指向本包的 `unit-step/proposal.json`，并使用另一个新输出目录。
这些命令会启动长仿真。原生驱动若与冻结来源不一致，先重新核对，不得编辑哈希强行复用。
