## 逐项调整与反馈

1. `merge` 只把 `GS_266199063` 改为仓库已冻结的协调占位程序。
   原来两个主要入口的未进入车辆降为零，全网未进入从 1381 减至 516。
   但最大字段误差从 58 升到 64，因此没有通过预先声明的保留条件，原始拒绝记录仍在。
2. `exit-stage` 从上述诊断分支出发，只删除 `266197525` 因剪枝而空置的 27 秒服务阶段。
   原始绿灯服务、黄灯与全红清空的对应来源均保留。
   它恶化为 MAE 15.107692、未进入 735，已拒绝。没有用它继续作时刻修正。
3. `retiming` 回到 `merge` 的诊断分支，只对原生已观测车辆作有界的发车时刻修正。
   既有路线和车辆标识保留，没有重新抽样整个 OD 时段。
   每个字段最多 64 辆，每辆最多移动 2700 秒。这是工程试验边界，不是文献规定的参数。
   反馈纳入主窗口 130 项及初始化小时的 52 项真实计数，总计 182 项。
   旧记录预测的改善不等于新原生计数，最终仍以本包的新完整运行判定。
   原生时刻修正实际恶化为 MAE 13.846154、未进入 766、182 项总绝对误差 2059，已拒绝。
4. `tail` 与 `tail27` 回到固定需求的 `merge` 分支，仅改变同一个绿灯交接量，分别为 18 秒和 27 秒。
   两项并行核验，保留 90 秒周期、黄灯、全红清空、路线及全部车辆请求。
   阶段候选必须满足已声明的 MAE、积压和安全门槛，182 项总绝对误差也不得超过 1883。
   然后按主窗口 MAE、最大误差和未进入量选择。各项原始单步保留判定仍完整保留。
   两项均被拒绝：未进入分别为 880 和 929，182 项总绝对误差分别为 1952 和 2197。
5. `original-seed-restored` 回到 `merge` 控制，从 `od-model.json` 的每个 `cells.initial_flow` 恢复 8640 辆。
   这些整数与各单元的模板数相等，全部 182 项字段时段的请求数精确对应原始目标。
   原生结果仍为 MAE 14.030769、未进入 744、在途 310、182 项总绝对误差 2113，因此被拒绝。

六项原始判定均为 `rejected`，没有选出通过阶段门槛的候选。
`merge` 的诊断 MAE 最低，但其原始拒绝继续生效。

## 单独保留的预检失败

`original-seed` 曾误用 `initial-od-vector.json`。该文件实际含 8622 辆，已经不是原始种子。
程序在核对 8640 辆及模板数时触发断言，尚未生成需求，也未启动原生运行。
`original-seed-preflight-failure.json`、原脚本、输入向量、模板模型及执行日志保留该失败。
其原生结果、计数误差和完成状态均为 `null`，不能写成零，也不计入六个完整结果。

`baseline-backlog-attribution.json` 保留全部请求的入口、字段和时段归属，未进入车辆没有被省略。
`baseline-merge-spillback.json` 保留接收车道满队及上游绿灯共同出现的原生样本。
缺少的队列报告保持未知，没有填成零。
`load-only-control-readback.json` 回读全部 50 个实际加载程序，确认两项控制调整分别只改变一个程序。
回读只确认模型中的活动程序，不证明现场实际配时。
Z15 信号组、LSA200 施工阶段、车道分配先验及现场 SPaT 的既有限制继续保留。
