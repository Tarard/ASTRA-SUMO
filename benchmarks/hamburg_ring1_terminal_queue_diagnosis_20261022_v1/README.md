# 汉堡终态读取与 K31/K2 车道小试验

本次诊断沿用 [完整入口候选](../hamburg_ring1_primary_entry_full_20261022_v1/README.md) 的原始状态和排队记录。
没有重测真实主窗。原结果仍为字段诊断 MAE 12.962、最大绝对误差 59，644 辆未进入、306 辆在途，未通过标定。

## 终态读取的范围

直接加载原生 14399.9 秒状态失败。SUMO 1.27.1 保存的 `7709833318` 两个信号程序含空 `state` 属性，读取器拒绝该值。
原文件和失败日志完整保留在 [失败读取记录](failed-original-load/)。
[1.27.1 的读取代码](https://github.com/eclipse-sumo/sumo/blob/v1_27_1/src/microsim/MSStateHandler.cpp#L474-L475) 仅在该可选属性存在时读取附加状态。
因此，另建查询副本，只省略这两项空属性。车辆、路线、车道归属、信号程序、相位和时刻均未改动。
原始状态、网络、控制文件和计数文件的校验值保持一致。

查询没有执行仿真步。前后时刻均为 14399.9 秒。
306 辆在途车的位置、速度、路线、车道归属及全部有效信号程序和相位均与保存记录一致。
但加载后的 24 项车道控制模式与原控制器记录不同，其中 19 项属于字段保持，5 项属于路口车身保持。
加载后的待进入查询返回空列表。原状态中的 644 辆未进入记录仍在，并与原完整运行未进入 ID 集合相同。
不能用这个空列表替代原来的 644 辆，也不能把查询副本作为已验证的续跑状态。
本状态没有保存路口接近关系记录。查询中未发现等待循环，不证明原运行没有局部死锁。
[逐项核对](analysis/snapshot-correspondence.json) 和 [完整查询](inspection/) 保留这些限制。

## K31/K2 通道的证据

最长等待集中于 Z.15 经 K31/K2 的路线。被检查车辆当前车道仍可合法延续路线，不能直接归为缺少转向或保持模式锁死。
20.377749 m 的缓冲道路 `142944325#0` 有两条合法汽车道。
终态记录中，车道 0 有三辆车，车道 1 为空。完整原生排队输出中，两条车道分别有 9701 和 771 个排队正值样本。
样本间隔为 1 秒。这些数量不是车辆数，也不证明另一车道有可用通行能力。
已安装程序中 K31 为每 90 秒的 51–84 秒放行，K2 为 56–82 秒放行，两者存在重叠。
不能根据单个终态的红灯或空车道断定瓶颈原因。
[排队与信号上下文](analysis/queue-and-signal-context.json) 保留原始数值。

随后只作 40 辆人工车的成对检验。两组路线、请求时刻、信号、道路权限和原有三处车身保持完全相同。
候选给其中 20 辆增加一处正速度经过点，引导其使用缓冲车道 1。
这是 SUMO 车道编号，不替代 MAP 进口车道编号。既有施工阶段不一致仍保留。

候选改变了车道使用，但没有增加 E1 贡献，也没有提前最后一次 E1 贡献。
逐车 E1 通过时刻平均晚约 0.155 秒。这个时间差不是标定 MAE。
本次不将其推广为容量修正。稀疏车流结果也不能证明它在原密集车流中一定无效。

## 观测设置更正与结果边界

首版误加 `freq=1800`，同时保留 `period=900`，原生仍输出 900 秒时段。请求的 1800 秒行因此缺失，未补零。
该版本保留在 [首版观测记录](failed-observer-probe/)。
第二版只改为 `period=1800` 并移除 `freq`，人工观测全部可用。
两版所有车辆的行程属性及每个 FCD 车辆采样均完全相同，见 [更正核对](analysis/buffer-probe-check.json)。
这个更正没有产生交通改善。

人工目标是 0–1800 秒聚合下的 13 行，不是原来的 130 个真实十五分钟字段目标。
40 个派生站点目标及全部真实残差仍保留在父完整运行中。本次未增加正式标定证据。
